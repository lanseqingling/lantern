# 版本管理与 Agent Apply

> **未来方向保留**
>
> 本文记录 Lantern 对版本管理和 Agent Apply 机制的一项未来设计方向，不代表当前产品行为、协议或开发默认方案。当前实现与未明确指定的后续开发仍以 [LCD](./lcd.md)、[Agent](./agent.md) 和[编辑器体验](./editor.md)中的 WorkingRevision、Candidate、ChangeSet、Apply 与 SavedSnapshot 规则为准。只有经过单独评审并明确决定实施后，本文才可转化为当前设计。

## 1. 设计目标

外置 Agent 适合连续完成创建页面、调整画格、放置图片、裁切和层级编排等一组相关操作。逐项要求用户 Apply 会打断任务，直接写入正式作品又会削弱创作者对最终结果的控制。

未来机制拟采用“任务内自由编辑、任务后整体审查”的方式：

- 一话内的确定性 MCP 操作直接进入隔离的 Agent 草稿，不逐项请求 Apply。
- Agent 完成任务后冻结草稿，生成稳定的版本对比链接。
- 用户审查整项任务的最终视觉与结构变化，再决定接受、保留或丢弃。
- 未经可验证的用户授权，Agent 不能把方案保存为正式版本。
- 漫画、一话和共享资源的破坏性操作不进入单话草稿，继续使用准确对象确认。
- 所有内部编辑仍经过 Capability、ChangeSet、所有权、幂等、revision 和作品校验，隔离草稿不是绕过领域边界的写入通道。

该方向保留 Lantern 的核心原则：Agent 可以自由完成过程，创作者掌握正式作品版本的关键决定。

## 2. 作用范围

是否进入 Agent 草稿不能只按“一话内”与“一话外”判断，还要考虑对象是否可以在单话范围内完整隔离。

| 范围 | 典型对象与操作 | 未来处理方式 |
|---|---|---|
| 一话作品内容 | 页面、真正双页、画格、图片、气泡、文字、阅读顺序 | 写入单话 Agent 草稿，完成后整体审查 |
| 单话生成结果 | 格内图片、布局方案、多对象结果 | Candidate 可在 Agent 草稿中被选用，最终随整项方案审查 |
| 漫画级共享资源 | 角色、场景、道具、视觉风格、漫画封面、资产图片槽 | 新资源和不可变图片版本可以先登记；修改、替换或归档共享事实需要独立审查或漫画级方案 |
| 作品结构 | 漫画、一话的创建、归档和删除 | 不进入单话草稿；破坏性动作要求准确对象和显式确认 |
| 多话操作 | 跨话重排、批量替换、整部作品变更 | 不属于首期；未来需要多分支原子方案 |

在隔离草稿中删除页面、画格或图片不会立即改变正式作品，因此不需要逐项打断用户；删除漫画、删除一话和归档共享资产会影响草稿之外的事实，不能仅依靠最终单话对比承接风险。

## 3. 核心模型

未来版本链路包含四个不同概念：

| 概念 | 含义 | 是否正式作品 |
|---|---|---:|
| `Candidate` | 单个生成、结构或其他需要选择的结果 | 否 |
| `AgentDraft` | 一次 Agent 任务在固定基准上连续编辑的隔离草稿 | 否 |
| `ChangeProposal` | AgentDraft 完成后冻结的待审方案 | 否 |
| `SavedSnapshot` | 用户接受并保存后的不可变阅读与导出基线 | 是 |

Candidate、AgentDraft 和 SavedSnapshot 不能互相替代：

- Candidate 可以作为 AgentDraft 的一个输入或中间选择。
- AgentDraft 聚合一次任务中的多个 ChangeSet，而不是一个大而不透明的命令。
- ChangeProposal 固定审查时看到的结果，后续继续编辑必须产生新的方案头。
- SavedSnapshot 只由正式接受产生，不能由普通 MCP 编辑静默创建。

```text
当前 WorkingRevision
        │
        └── AgentDraft
              ├── ChangeSet 1
              ├── ChangeSet 2
              ├── Candidate → ChangeSet 3
              └── ChangeSet N
                        │
                        ▼
               ChangeProposal
                  ├── 接受并保存为新版
                  ├── 保留方案
                  └── 丢弃方案
```

“Agent 草稿”是创作中的可变头，“待审方案”是不可变审查结果，“保存版本”是正式作品基线。用户界面不应把三者都简称为“版本”。

## 4. AgentDraft

### 4.1 创建

一次外置 Agent 任务开始修改一话时，Lantern 基于当时最新 WorkingRevision 创建 AgentDraft，并固定：

- 所属用户、漫画、一话和 Project；
- `baseRevision`；
- 初始 LCD 与固定资源版本引用；
- 发起任务或外置宿主信息；
- 创建时间、过期策略和当前状态。

首期一个 AgentDraft 只能属于一话。Agent 不需要把内部 Project ID、revision ID 或草稿 ID 暴露给用户；自然语言、Lantern 链接和稳定引用仍由 MCP 解析。

### 4.2 编辑

AgentDraft 内的每次 MCP 编辑：

- 只能调用已登记的语义 Capability；
- 固定草稿内部的预期 revision；
- 产生一个原子 ChangeSet；
- 全部命令校验成功后才前进草稿 revision；
- 保留幂等键、审计信息、作用对象和资源版本；
- 支持草稿内部失败恢复和任务续跑；
- 不改变正式 WorkingRevision、SavedSnapshot、阅读预览或导出。

用户不需要逐项 Apply。这里的“直接执行”只表示变更已经进入 AgentDraft，不表示已经进入正式作品。

### 4.3 中间 Candidate

任务中的生成式图片、结构方案或高风险多对象结果仍可先产生 Candidate。Agent 可以根据用户任务和 Skill 在 AgentDraft 内选择、组合或放弃这些结果，但只能把被选中的结果应用到草稿。

这样可以减少过程打断，同时确保：

- Candidate 不会直接覆盖正式工作稿；
- 最终对比能够显示生成结果对整页或整话的实际影响；
- 用户接受的是完整方案，而不是脱离上下文的单张图片。

### 4.4 生命周期

AgentDraft 至少包含以下状态：

| 状态 | 含义 |
|---|---|
| `active` | Agent 正在修改或可以继续修改 |
| `ready` | Agent 已完成任务，可以冻结审查 |
| `superseded` | 同一任务产生了更新草稿头，旧草稿不再继续编辑 |
| `expired` | 超出保留期限且未被保留 |
| `failed` | 无法继续，但已经完成的草稿 revision 可用于诊断 |

任务取消或宿主会话删除不能破坏正式作品。是否保留失败草稿由资源回收规则决定。

## 5. ChangeProposal 与对比链接

Agent 完成任务后，将当前 AgentDraft 头冻结为 ChangeProposal。冻结后：

- 对比内容、基准 revision 和资源引用不可原地改变；
- Agent 继续修改时必须从当前草稿产生新的方案；
- 旧方案仍可查看，但可以标记为已被新方案取代；
- 没有实际差异的草稿不能伪装成可保存的新版本。

ChangeProposal 同时提供稳定 Lantern 引用和本地审查链接：

```text
lantern://change-proposals/{proposalId}
http://localhost:{webPort}/reviews/{proposalId}
```

链接只包含稳定方案身份，不携带安装令牌、对象存储签名或内部命令。打开链接后仍校验当前本地用户和方案归属。

## 6. 对比界面

审查页面需要同时表达结构差异和最终视觉差异，不能只展示命令列表。首期至少包括：

- 任务标题、Agent 摘要、创建时间和影响范围；
- 基准版本、方案版本和当前工作稿状态；
- 新增、删除、复制、移动或重排的页面；
- 画格几何、边框、层级、阅读顺序和出血变化；
- 图片版本、位置、裁切、归属和破格变化；
- 气泡、文字和其他可见元素变化；
- 每页修改前后缩略图；
- 修改前/修改后切换；
- 适用时提供左右对比或透明叠加；
- 不能渲染、资源缺失、校验失败和 revision 冲突；
- 接受并保存、保留方案、丢弃方案三个明确动作。

对比应提供两种差异：

1. **任务差异**：`baseRevision → ChangeProposal`，说明 Agent 本次做了什么。
2. **当前影响**：`当前 WorkingRevision → ChangeProposal`，只在用户同时修改了正式工作稿时出现，用于判断是否仍可接受。

视觉结果和结构摘要必须来自同一个冻结方案，不能在页面刷新后分别读取不同 revision。

## 7. 三种审查结果

### 7.1 接受并保存为新版

该动作表示用户同时同意：

- 接受 Agent 对一话的全部方案变化；
- 将方案提升为新的正式 WorkingRevision；
- 创建新的不可变 SavedSnapshot；
- 让后续阅读预览和导出读取该保存版本。

如果 AgentDraft 基于包含尚未保存的人工编辑的 WorkingRevision，保存版本也会包含这些基准内容。审查页需要明确提示“该版本包含任务开始时已有的工作稿变化”，避免用户误以为只保存 Agent 的差异。

### 7.2 保留方案

保留方案用于收藏一个尚未采用的方向，不改变正式工作稿和 SavedSnapshot。用户以后可以：

- 重新打开对比；
- 复制方案链接；
- 基于该方案继续派生；
- 在仍满足版本前置条件时接受。

产品概念可以描述为“保留为候选快照”，但界面建议显示“保留方案”，避免与 Candidate 和正式 SavedSnapshot 混淆。领域状态仍属于 retained ChangeProposal，而不是另一种 SavedSnapshot。

### 7.3 丢弃方案

丢弃后：

- 正式工作稿和保存快照保持不变；
- 方案进入不可继续接受的终态；
- 审计摘要可以保留；
- 仍被其他作品、草稿、方案或快照引用的 AssetVersion 不得删除；
- 无引用的临时对象由后续垃圾回收处理，不在用户点击时同步物理删除。

## 8. 正式接受的原子边界

接受方案必须在一个受控事务中完成：

1. 校验用户、漫画、一话、Project 和方案归属；
2. 校验 ChangeProposal 仍处于可接受状态；
3. 校验当前 WorkingRevision 与方案 `baseRevision`；
4. 校验 LCD、对象 ID、页面结构和固定资源版本；
5. 创建一个新的正式 WorkingRevision；
6. 创建对应 SavedSnapshot；
7. 标记 ChangeProposal 已接受并记录目标 revision；
8. 提交后再更新读取模型和审查状态。

任一步失败都不能改变正式作品。重复调用同一接受请求必须通过幂等键返回同一结果，不能创建多个 SavedSnapshot。

接受后的正式 WorkingRevision 只记录一次任务级提升，不需要把草稿内部的每个 revision 复制到正式 Undo 历史。草稿中的 ChangeSet 仍保留为审计与对比依据。

## 9. Revision 冲突

AgentDraft 创建后，用户仍可能继续在工作台编辑同一话。首期采用保守冲突策略：

- ChangeProposal 始终可以查看和保留；
- 当前 WorkingRevision 等于 `baseRevision` 时可以直接接受；
- 当前 WorkingRevision 已前进时，方案标记为冲突，不得自动覆盖；
- 用户可以要求 Agent 基于最新工作稿重新执行；
- 不自动合并页面顺序、删除页面、跨页对象和多对象结构变化。

未来可以对明确不相交的对象提供 rebase，但必须满足：

- 对象身份稳定；
- 两边未修改同一属性或结构关系；
- rebase 后重新生成对比；
- 原方案保持不可变；
- 用户接受的是 rebase 后的新方案。

## 10. 用户授权与 Agent 接受

### 10.1 默认规则

默认情况下，Agent 可以：

- 创建和修改 AgentDraft；
- 冻结 ChangeProposal；
- 返回审查链接；
- 根据用户要求保留或丢弃方案。

Agent 不能在没有可验证授权的情况下执行“接受并保存为新版”。Skill 中的行为要求不是服务端授权证明，外置宿主传入 `confirmed: true` 也不能单独证明用户已经同意。

### 10.2 审查页确认

默认可信路径是用户在 Lantern 审查页点击“接受并保存为新版”。该动作由 Lantern 自己的身份和确认界面承接，不依赖外置 Agent 转述。

### 10.3 用户要求 Agent 代为选择

用户可以自然语言告诉 Agent 接受某个方案，但最终写入需要以下任一可验证条件：

- Lantern 为该方案展示一次确认，并产生短时效、单次、绑定 `proposalId` 和 `accept` 动作的授权；
- MCP 宿主提供 Lantern 可验证的用户确认回执；
- 用户已经在 Lantern 设置中明确开启适用范围内的自动接受权限。

一次性授权不能转用于其他方案、其他一话或其他动作，过期和重复使用都必须失败。

### 10.4 自动接受权限

设置中的未来能力建议命名为“允许自动接受 Agent 方案”，默认关闭。权限至少区分：

- 仅本次任务；
- 当前一话；
- 当前漫画；
- 始终允许低风险单话方案。

即使用户开启自动接受，以下动作仍不得自动执行：

- 删除或归档漫画；
- 删除或归档一话；
- 归档共享资产；
- 多话批量修改；
- 基准 revision 已冲突的方案；
- LCD、资源或渲染校验未通过的方案。

自动接受必须保留审计记录、结果通知和可访问的对比链接。用户需要能够随时关闭权限，关闭后未执行的授权立即失效。

## 11. 一话外与破坏性操作

漫画、一话和共享资源的破坏性动作不使用 ChangeProposal 的“接受并保存”语义，因为它们不是一话 SavedSnapshot 的内容变化。

推荐流程：

```text
Agent 提出操作
  → Lantern 解析准确对象
  → 返回对象名称、所属关系和影响范围
  → 用户显式确认
  → 执行归档或可恢复删除
```

这类操作可以拥有独立的 PendingAction 或 ApprovalRequest，但不应伪装成单话 Candidate 或 AgentDraft。可恢复时优先归档或进入回收站，物理删除另设生命周期。

## 12. 资源与垃圾回收

AgentDraft 可以引用新上传或宿主生成的不可变 AssetVersion。二进制资源登记与正式作品采用是两个阶段：

- 上传和登记 AssetVersion 可以在任务过程中完成；
- 未被正式作品采用的版本仍可被 AgentDraft 或 ChangeProposal 引用；
- 保留方案必须固定其全部资源版本；
- 丢弃或过期后，仅无任何引用的对象可以进入回收队列；
- 漫画共享资产的名称、描述、主图和归档状态不能由单话草稿隐式改写。

垃圾回收需要覆盖 AgentDraft、ChangeProposal、Candidate、WorkingRevision 和 SavedSnapshot 的完整引用图，不能只查询当前工作稿。

## 13. 审计与可恢复性

每个 AgentDraft 和 ChangeProposal 至少记录：

- 所属用户、漫画、一话和 Project；
- 基准与草稿头 revision；
- 创建、冻结、保留、丢弃或接受时间；
- 发起宿主和任务引用；
- 每个 Capability、目标、幂等键与结果；
- 新增或固定的 AssetVersion；
- 用户授权来源和权限范围；
- 接受后的正式 revision 与 SavedSnapshot；
- 失败、冲突、过期和资源校验原因。

审计数据只保存可验证的操作事实，不保存宿主模型的思维链。删除宿主会话不能删除已经接受的作品版本或仍被保留方案引用的资源。

## 14. 首期收敛边界

如果未来决定实施，第一版建议限制为：

1. 一个任务只创建一个单话 AgentDraft。
2. 只允许当前已经开放的一话内页面、画格和图片 Capability 写入草稿。
3. 草稿内操作不逐项 Apply，但仍产生原子 ChangeSet。
4. 完成后冻结为一个 ChangeProposal 并生成本地审查链接。
5. 审查页提供接受并保存、保留方案和丢弃方案。
6. 接受时原子创建正式 WorkingRevision 与 SavedSnapshot。
7. 默认只有 Lantern 审查页可以完成正式接受。
8. revision 变化时拒绝接受，不做自动合并。
9. 共享资产修改、漫画和一话删除继续使用当前独立确认机制。
10. 多话方案、方案合并、自动 rebase 和自动接受暂不进入首期。

## 15. 实施前置决策

正式实施前仍需明确：

- AgentDraft 从当前 WorkingRevision 还是最近 SavedSnapshot 分叉；本设计倾向当前 WorkingRevision，以保持用户正在编辑的上下文。
- 接受是否始终同时创建 SavedSnapshot；本设计首期倾向“接受并保存”单一语义。
- 保留方案的默认期限、数量限制和资源配额。
- 审查页需要支持的最小视觉 diff 和结构 diff。
- 外置 MCP 宿主如何提供可验证的单次用户确认。
- 自动接受权限是安装级、漫画级还是一话级配置，以及如何撤销。
- 正式 Undo 是否回退整个任务级提升，还是只提供“回到上个保存版本”；首期倾向把接受视为一个整体单位。
- UI 人工编辑和 AgentDraft 是否允许同时进行；允许时必须采用本文的冲突策略。

这些问题未决时，不应只为了减少 Apply 次数而让外置 Agent直接写入并保存正式作品。
